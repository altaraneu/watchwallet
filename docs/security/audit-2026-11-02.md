# Independent code review of v1.0.0, 2026-11-02

Source: a two-part review by a separate Claude session, requested by the project owner. It reviewed
tag `v1.0.0` (commit `ab4a46a`) and commit `44739f6`. It read source code and did not run the app.
It is an AI code review, not a professional security audit. The original report is in Czech; this is
an English summary. It gave no overall "safe" verdict.

All items are planned for version 1.1. Status changes only with evidence from code or a test. Commit
hashes refer to `rework-integration`; tests ran on Windows with no device, see the last section.

Status: `open`, `in progress`, `fixed` (commit or test named), `documented` (cannot be fully solved),
`owner` (needs the project owner).

### Portfolio figure, found while testing

Not from the review. On test data the header "Excluding deposits and withdrawals" showed about 33 USD less
than a recomputation from transactions. `open`: **the 33 USD is not attributed**, as the database was not
available for this work. What the code shows, with `ChartHistoriesTest`:

- Fees and chart sampling are not the cause: both calculations treat them identically
  (`.aFeeIsALossAndCountsTheSameInBothCalculations`, `.theSamplingOfTheChartDoesNotChangeTheFlows`).
- The definitions differ in ways that are defensible: transactions older than the first known price count
  at that price, and coins the history does not explain are part of the first value of the chart
  (`.theDifferenceToARecomputationIsExactlyTheSumOfItsTerms`). Each has the sign of the difference found.
- A real bug in the neighbourhood, of the opposite sign, so it cannot explain the difference: an asset with
  no price history read a deposit as a gain. `fixed` `dd67781`; `.aDepositOfAnAssetWithoutPriceHistoryIsNoGain`.

## Reported as sound

The review found no signing or transaction-sending code, no author server, no analytics or dynamic
code loading in the reviewed code, and logs in debug builds only. Donation addresses appear only in
`DonationAddresses.kt` and match the README. Backup encryption is AES-256-GCM with PBKDF2-SHA256 at
600,000 iterations and random salt and IV. The chart library and `gradle-wrapper.jar` match official
files. Who owns the donation addresses cannot be shown from code.

## What the review did not cover

Transitive dependencies and the merged manifest, chain adapters line by line, price and portfolio
repositories, the database, full settings screens, iOS code, tests, translations, native binaries and
the Gradle distribution checksum. The review will be repeated on the 1.1 code.

## Limits that will remain

- Cardano (A3-H1): a base address is a payment hash and a stake hash, independent of each other. From a
  `stake1` key alone the app can check the stake hash, and only the wallet's keys could check the payment
  hash. So a dishonest server can pair its own payment key with the wallet's stake key, and that address
  passes every check the app can make, while a payment to it goes to the server's owner. Comparing it
  with a wallet app works only if people do it, so the app no longer shows such an address. `stake1`
  wallets show the stake key, which cannot receive; a receive address comes from the wallet app. The
  cost is a convenience, not any balance or history, and `account_addresses` is no longer requested.
- Some secrets cannot be told apart from addresses by format, so the app cannot promise to catch all.
- Data providers must see the address they are asked about, plus the IP address unless a proxy is used.
